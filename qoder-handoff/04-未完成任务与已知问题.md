## 2. 已知问题（有复现步骤）

### KN-01 · Nosana `qwen2.5-3b` 对 v2 长 Prompt 遵循度有限 → 多数解释走模板降级

- **现象**：详情页 AI 卡渲染完整（headline / 城市优势 / 三段小行程 / 便利度 / 取舍），但后端日志 `fallback=` 常非 `none`，即模型原始输出未过 `RichNarrativeValidator`。
- **复现**：`docker compose logs api | grep stopover_explanation_completed`，观察 `provider=` 与 `fallback=` 分布。
- **根因**：RTX 3060 上跑 3b-AWQ（~25 tok/s），v2 Prompt 要求严格 JSON + evidenceKeys 绑定，小模型易漏字段/夹带金额（validator 的 `MONEY_RE/REPEAT_RE` 会拒）。
- **影响**：**对演示无影响**（`RichTemplateNarrator` 与真模型同结构，且模板输出也必须过 validator）。属于「AI 参与度」的诚实口径问题 —— 别在视频里说「全部由模型生成」。
- **可能修法**：换 ≥7B 指令模型（延迟上升）、或放宽 validator 非安全类约束（**不建议**放宽金额/签证保证/复述三类）。

### KN-04 · `docker compose` shell 环境变量覆盖 `.secrets` 值（历史踩坑，最容易复发）

- **现象（曾发生）**：容器拿到**旧的** Nosana endpoint → 503，而 `.secrets/layoverjoy.env` 是对的。
- **根因**：`docker-compose.yml` 用 `NOSANA_OPENAI_BASE_URL: ${NOSANA_OPENAI_BASE_URL:-<硬编码默认>}`，`environment:` 块**优先级高于 `env_file`**，而 `${VAR}` 由**宿主 shell**（或 compose 自动读取的 `project/.env`）解析 —— 于是终端里残留的 `export NOSANA_*` 会静默覆盖 `.secrets` 的值；没 export 时则被 compose 里的硬编码默认覆盖。
- **修法**：改配置后 `unset NOSANA_OPENAI_BASE_URL NOSANA_DEPLOYMENT_ID NOSANA_MODEL DAYTONA_MODE` 再 `docker compose up -d --force-recreate api`；验证方式：`docker exec project-api-1 env | grep NOSANA_`（看值不看名）。
- **同一坑的另一面**：`.secrets` 里 `NOSANA_DEPLOYMENT_URL`、`ATLAS_TRANSACTION_MODE`、`DAYTONA_SANDBOX_ID` **不在 Zod schema 中，被 compose 注入后直接被代码忽略**（zod `z.object` 会剥离未知键）。真正生效的是 05 号文档里标的「生效来源」。

### KN-05 · 旧方案快照仍能打开（契约双保险，非 bug）

`requiredDocuments` 契约升级为对象数组后，DB 里仍有字符串数组旧快照；后端 `normalizeRequiredDocuments()` 归一 + Android `RequiredDocumentSerializer` 兼容，两层都必须在（防止本地缓存/旧接口数据再崩）。删掉任一层都会回归 → 见 `08` §1。

### KN-07 · Nosana 部署周期性 503「Service Initializing」（**交接当日已发生并自愈；次日复查已全绿**）

- **实测时间线**：12:12:14 开始 `/models` 返回 503（每次 0.7–1.0s）→ 连续 13 次全失败 → **12:18:18 自动恢复 200（1.06s）**，全程未人工干预。`/health`、`/api/chat`、`/api/models` 在该窗口内一致 503。
- **2026-08-30 12:34 复查（当前状态：健康）**：`${BASE}/health` → **200**、`$BASE/models` → **200 1.08s**、`$BASE/chat/completions`（真实模型 `layoverjoy-qwen2.5-3b`）→ **200** 且返回正常 completion；`docker compose logs app` 无 503/narrat 报错；自检脚本第 8 节 `PASS  Nosana … /models → 200 1.083766s`。
- ⚠️ **复查中拿到的新结论（比“自愈”更重要）**：**容器根路径 `/` 恒定 503**（无 handler，网关直接返「Service Initializing」HTML），与实例是否就绪**无关**：实测同一秒根路径 503 而 `/health` 200。因此：
  - 探活**必须**打 `$B/models` 或 `${B%/v1}/health`（`B=NOSANA_OPENAI_BASE_URL`）；
  - **禁止**把 `NOSANA_DEPLOYMENT_URL`（根路径）当健康检查，否则会把完全正常的服务读成“持续故障”；
  - 判定“真未就绪”的最小证据是 **`/health` 或 `/v1/models` 本身 503/超时**，不是根路径。
- **已排除的原因**：不是配置错 —— 容器内 `NOSANA_OPENAI_BASE_URL / NOSANA_DEPLOYMENT_ID / NOSANA_MODEL` 三项与 `.secrets` 逐字一致，`/v1/integrations` 的 `deploymentIdTail=XW5811vR` 也对得上；不是网络 —— 同一窗口内 Atlas 主机 HTTP 200、SMTP 465 可达。
- **根因**：部署侧 GPU 实例**休眠/冷启动**（无人请求时被回收，首次请求触发拉起）。属于**外部运行实例行为**，不是应用缺陷；与 `08` §3「模型输出为空」同族但处置不同（那个需重启 deployment）。
- **影响面**：只影响 AI 叙事层。入境资格、报价、预订、监控全部不受影响；`RichTemplateNarrator` 会接住（UI 同构），所以**应用不崩、不白屏**，但视频里不能说“全部由真实模型生成”。
- **标准处置**（录制/演示前必做，已写入 07 §0）：
  1. 先探测 `/models`；503 就进一个方案详情页“踢一脚”再轮询（拉起靠真实请求）；
  2. 等到 200 后**立即预热目标方案的中/英解释各一次**（进缓存，录制时不再经 GPU）；
  3. 超过 ~10 分钟不恢复才去 Nosana 控制台 restart deployment；
  4. 实在不回来则**不特写 AI 卡**，改讲「确定性事实 + 同构模板兼容层」，把重心放在规则引擎与 Atlas 真报价上。
  5. ⚠️ **不要**改后端代码/Provider/Atlas 凭据来“绕过”它 —— 那是外部实例问题，改代码只会引入新风险。
- **探测命令**（只读，只看 `/health` 与 `/v1/models`）：
  ```bash
  B=$(grep NOSANA_OPENAI_BASE_URL ../.secrets/layoverjoy.env | cut -d= -f2-)
  curl -s -o /dev/null -w 'health=%{http_code}\n' "${B%/v1}/health"      # 200 即就绪
  curl -s -o /dev/null -w 'models=%{http_code}\n' "$B/models"           # 200 即就绪
  # 503/超时才需预热；切勿探测 $NOSANA_DEPLOYMENT_URL 根路径（恒 503）
  until [ "$(curl -s -o /dev/null -w '%{http_code}' -m 15 "$B/models")" = "200" ]; do sleep 20; done; echo UP
  ```
