## 1. `requiredDocuments` JSON 类型不一致 → 方案详情页白屏（最新，commit `7932a042`）

**症状**

```
Unexpected JSON token: Expected beginning of the string, but got {
at path: $.eligibility.requiredDocuments[0]
```
Android 打开「方案详情」抛 `JsonDecodingException`，整页崩溃。

**根因**：13 号方案的 v2 规则引擎把 `requirements` **对象数组**写进 `EligibilitySnapshot.requiredDocsJson`，而 `EligibilityDetailDto.requiredDocuments` 仍是 `List<String>`。
⚠️ 我第一次的处置是**把后端降级成字符串数组**（`typeof r==='string' ? r : (r?.descriptionZh ?? r?.code ?? JSON.stringify(r))`）—— 那是错误的临时妥协，违反正式契约，本次已纠正。

**修法（三层，缺一不可）**

| 层 | 位置 | 做法 |
|---|---|---|
| 契约 | `backend/src/plans/plans.service.ts` | 导出 `normalizeRequiredDocuments()` + `REQUIRED_DOC_I18N` 双语码表；输出恒为 `{code, mandatory, descriptionZh, descriptionEn, factPaths}[]`。`null→[]`；字符串→对象（mandatory=true + 双语文案）；对象补默认；无效项**跳过并记脱敏 warning**（只记 idx + 类型）；**单条脏数据不得让整个接口失败** |
| 传输兼容 | `android/.../data/Models.kt` | `RequiredDocumentDto` + `RequiredDocumentSerializer`（string-or-object 自定义反序列化，未知字段忽略）—— 防本地缓存/旧接口数据 |
| 渲染 | `PlanDetailScreen.kt` | 「所需旅行证件」：当前语言的 `description` → `doc.code.<CODE>` i18n 名 → 原始 code 三级回退；`mandatory` 显示「必须」；空数组**不渲染卡片**；绝不 `toString()` 对象 |

**最终契约**（`fixtures/api/plan-detail-required-documents.json` 有完整脱敏样例 + `legacyInputs` 旧形态）：

```json
{"eligibility":{"status":"ELIGIBLE","requiredDocuments":[
  {"code":"PASSPORT_VALID_6_MONTHS","mandatory":true,
   "descriptionZh":"护照剩余有效期至少六个月","descriptionEn":"Passport valid for at least six months",
   "factPaths":["traveler.passport.expiryDate"]}]}}
```

**防回归**：`backend/test/required-documents.spec.ts`（8 例：对象/字符串/null/非数组/混合/未知字段/无效跳过/结构统一）+ `android/app/src/test/.../RequiredDocumentsParsingTest.kt`（5 例）。
**禁止的回退**（用户明确不接受）：改成 `List<Any>`、改 `JsonElement` 后不渲染、catch 后静默隐藏整个 eligibility、删字段。

**踩到的次生坑**：kotlinx 自定义 serializer 需要 `import kotlinx.serialization.json.jsonPrimitive`（漏了会编译期报 unresolved），并且**不要** import 不存在的 `DeserializerForNullable`。

## 2. `docker compose` 静默用旧配置（最容易复发）

**症状**：容器里 Nosana endpoint 是**旧部署地址** → 503/超时，而 `../.secrets/layoverjoy.env` 明明是对的。

**根因**：`docker-compose.yml:51-53` 写成 `NOSANA_OPENAI_BASE_URL: ${NOSANA_OPENAI_BASE_URL:-<硬编码默认>}`。
① Compose 的 `environment:` 块**优先级高于 `env_file:`** → `.secrets` 的同名值被丢弃；
② `${VAR}` 由**宿主 shell**（或 compose 自动读的 `project/.env`）解析 → 之前 `export NOSANA_*` 的残留会赢过一切；
③ 都没有时用硬编码默认。

**修法**：
```bash
unset NOSANA_OPENAI_BASE_URL NOSANA_DEPLOYMENT_ID NOSANA_MODEL DAYTONA_MODE
docker compose up -d --force-recreate api
docker exec project-api-1 env | grep NOSANA_     # 看「值」，不是看变量名存不存在
curl -s localhost:8080/v1/integrations | python3 -m json.tool   # deploymentIdTail 对不对
```
**长期建议**：要么去掉 `${VAR:-default}` 的 default（逼显式配置），要么把默认值删到与 `.secrets` 一致。任何默认值都会**覆盖** `env_file` 同名项 —— 这是 compose 语义，不是 bug。

## 3. Nosana 推理：API 风格与耗时

| 问题 | 结论 |
|---|---|
| OpenAI 兼容口 `/no_think`、`think:false` **不生效** | vLLM/Ollama 兼容层忽略；必须走**原生** `/api/chat` + `{"think": false, "format": "json"}` → 45s 降到 ~4s |
| 部署是 vLLM 栈时没有 `/api/chat`（404/405） | `nosana.service.ts` 的 `chatRich()` 做**风格自适应**：先试 native，404/405 回退 OpenAI `/v1/chat/completions`。别写死一种 |
| 3060 上想 <2s | **不可达**：~1s 网络底 + ~25 tok/s。要么接受 ~2–4s，要么换更大显存/更小模型 |
| 模型退化（content 为空、reasoning 全是 `///`） | 部署侧异常，需在 Nosana 管理页**重启部署**（本项目发生过，用户手工重启解决），不是后端 bug |
| AI 输出夹带金额/复述天数/自称模型 | `RichNarrativeValidator` 三类正则拦截：`MONEY_RE`（含 `SGD 120` 前缀式，最初漏过、已补 `(SGD|USD|…)\s*\d` 分支）、`TECH_RE`（nosana/ollama/qwen/gpu/deployment…）、`REPEAT_RE`（停留 N 天 / N 小时 / usable hours / JoyScore…） |
| 首请求慢、并发重复打爆 GPU | `explainRich(cacheKey,…)` 用 `inflight` Map 做 **single-flight**；缓存键 `SHA-256(planId\|lang\|行程\|interests\|sort,pace,catalogVersion,promptVersion).slice(0,24)` |

## 4. NestJS + Fastify 的两个细节

- **`res.setHeader is not a function`**：Fastify 适配器下不要手写 `@Res() res`。改用 Nest 装饰器 `@Header('Cache-Control', 'public, max-age=300')`（`/v1/airports/*` 匿名缓存接口就是这么修的）。
- **`@Header` 与 `@Res` 混用**依旧会崩 —— 只保留装饰器路径。

## 6. 后端 v2 规则引擎的三个逻辑陷阱

1. **旧 spec 用位置参数构造服务** → 给 `BookingsService` 新增 `assessV2` 构造参数后，旧 `bookings-saga.spec.ts` 静默错位、抛 `TypeError`（不是断言失败，最难查）。**改构造签名必须同步所有 spec 的 `buildService()`**；断言改为 `expect(assessV2.assess).toHaveBeenCalledWith(expect.objectContaining({mode:'BOOKING'}), expect.anything())`。
2. **评估中转地时 `destination.country` 必须优先取 `stopover.country`**，否则航段末点（最终目的地）与评估对象（中转国）不一致，规则叶子误判 FALSE → 该出的方案出不来。
3. **`isHard()` 判定过窄/过宽都会翻转结论**：`op === 'VALID_FOR_DAYS' || ((LTE||GTE) && fact.startsWith('traveler.history.'))`。硬事实 FALSE → 直接 `INELIGIBLE`；聚合顺序固定为 **负向 TRUE → hard FALSE → relax → TRUE**。
4. 搜索期放宽只适用于**仅缺** `documents.*` / `traveler.history.*` 的情形，且 `TRANSIT_TOUR_PROGRAM` 类别**不放宽**；预订模式至少要 `NEEDS_REVIEW`。

## 10. 写 Shell 脚本时本会话真实踩到的五个坑（都已修进 `scripts/*.sh`）

1. **`$VAR` 后面紧跟全角标点会被吸收进变量名**。`"…：$SECRETS_FILE（$CNT 个变量）"` 在 `set -u` 下直接报
   `SECRETS_FILE（: unbound variable` 并**中断脚本**。原因：本环境下 bash 把多字节字符当作标识符字节。
   → **中文脚本里所有变量必须写 `${VAR}（…）`**，或在括号前留空格。自检：
   `grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]' scripts/*.sh`（零命中才算干净）。
2. **`java -version 2>&1 | head -1 | grep -oE …` 取值为空**。`pipefail` + `head` 提前退出的 SIGPIPE 组合下，整条管道拿不到输出，导致报“Java 主版本 = unknown”。
   → 改为**一次 sed 抽取**：`java -version 2>&1 | sed -nE 's/.*version "([0-9]+)[^"]*".*/\1/p' | head -1`。
3. **`bash /dev/tcp/host/port` 在受限 shell 里会被 `Killed: 9`**，表现为“SMTP 端口不可达”的**假 FAIL**（实际 python 探同一端口秒连）。
   → 探测函数先试 `nc -z -G 8`，无 `nc` 时回退 `python3 socket.create_connection`。
4. **PostgreSQL `coalesce(date_col, '-')` 报 `invalid input syntax for type date`**（date 与 text 不可混）。
   → 写 `coalesce("asOf"::text, '-')`。本项目 `EntryRuleSet` 的正确查法已固定在 `check-local-environment.sh` 里（输出 `ACTIVE/2.0.0 asOf 2026-08-30`）。
5. **拿 `NOSANA_DEPLOYMENT_URL` 的根路径当健康探针 → 永久假故障**。该 URL 指向推理容器根路由，**没有任何 handler**，网关恒返回
   503 + HTML「Nosana Network - Service Initializing」（实测 2026-08-30 12:34 连打 3 次全 503，而同一秒 `/health`、`/v1/models`、`/v1/chat/completions` 全 200）。
   → 探活只认 `${NOSANA_OPENAI_BASE_URL%/v1}/health` 或 `$NOSANA_OPENAI_BASE_URL/models`；后端 `nosana.service.ts:188` 也是从 `NOSANA_OPENAI_BASE_URL` 反推 root 再拼路径，从不使用 `NOSANA_DEPLOYMENT_URL`。

**方法论**：脚本写完必须**实跑一遍再看输出**。“`bash -n` 语法通过”不等于能跑完 —— 上面四个坑里前三个 `bash -n` 全部不报。
