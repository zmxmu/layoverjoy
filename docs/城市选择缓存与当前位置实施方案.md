# LayoverJoy 城市选择缓存、智能日期与当前位置实施方案

## 1. 文档目标

本方案用于完善 LayoverJoy 搜索入口的三个高频体验问题：

1. 用户每次进入搜索页都需要重新选择出发地、目的地和停留条件。
2. 缓存中的出发日期过期后，页面可能继续显示过去日期或不合理日期。
3. 用户身处当前城市时，仍需手动搜索并识别对应机场。

本次只增强搜索入口，不引入地图页面、持续定位、后台定位或新的付费地图服务。

## 2. 产品结论

### 2.1 必须实现

- 按登录用户缓存上一次搜索设置。
- 再次进入搜索页时自动恢复有效设置。
- 对过期出发日期进行确定性滚动，而不是简单清空。
- 出发城市选择页增加“使用当前城市”。
- 定位结果匹配到城市后，仍允许用户选择该城市下的具体机场或全部机场。
- 定位失败、权限拒绝、设备不支持时，手动城市搜索必须保持可用。

### 2.2 本期不实现

- 不展示 Google Map。
- 不接入 Google Places Autocomplete。
- 不申请后台定位。
- 不持续追踪用户位置。
- 不把经纬度上传到后端。
- 不根据定位自动提交搜索。

## 3. Google 定位服务与 API Key 结论

推荐使用 Google Play services Location 的 `FusedLocationProviderClient` 获取一次前台位置。

- 只需要 Android 依赖 `com.google.android.gms:play-services-location`。
- 不需要 Google Maps SDK。
- 不需要 Google Maps Platform API Key。
- 不需要为这一项启用 Google Cloud Billing。
- 只请求 `ACCESS_COARSE_LOCATION`，城市级匹配不需要精确定位。
- 使用 `getCurrentLocation()` 获取单次位置，不申请后台权限。

官方依据：

- [FusedLocationProviderClient](https://developers.google.com/android/reference/com/google/android/gms/location/FusedLocationProviderClient)
- [Android 定位权限](https://developer.android.com/develop/sensors-and-location/location/permissions)

如果未来加入 Google 地图、Places 搜索、地点详情或 Google Place Autocomplete，则需要 Google Cloud 项目、API Key、API 限制和 Billing。Places API 按请求及 SKU 计费，本期不要引入。

- [Places API 用量与计费](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing)

Android `Geocoder` 可以作为可选降级，但官方不保证其可用性或准确性，因此不能把它作为城市识别的唯一来源：

- [Android Geocoder](https://developer.android.com/reference/android/location/Geocoder)

## 4. 搜索设置缓存

### 4.1 缓存范围

缓存以下字段：

| 字段 | 格式 | 说明 |
| --- | --- | --- |
| `originCityCode` | String? | 出发城市 IATA 城市代码 |
| `originAirportCodes` | List<String> | 用户选中的一个或多个机场 |
| `destinationCityCode` | String? | 目的地城市代码 |
| `destinationAirportCodes` | List<String> | 目的地机场集合 |
| `departureDate` | `YYYY-MM-DD` | 上次选择的出发日期 |
| `preferredLeadDays` | Int | 用户选择日期时距离当日的天数 |
| `preferredDepartureDayOfWeek` | Int | 1 至 7，保留用户偏好的星期 |
| `minStopoverDays` | Int | 最少停留天数 |
| `maxStopoverDays` | Int | 最多停留天数 |
| `maxExtraPriceSgd` | Decimal? | 可接受额外票价 |
| `originSelectionSource` | Enum | `MANUAL` 或 `CURRENT_LOCATION` |
| `updatedAt` | ISO Instant | 最近修改时间 |
| `schemaVersion` | Int | 缓存结构版本，初始为 1 |

### 4.2 存储方式

- 优先复用项目已有 DataStore。
- 如果项目已经使用 Preferences DataStore，则不要再引入 Room。
- 缓存按当前 `userId` 隔离，避免同一设备切换账号后互相读取搜索偏好。
- 未登录状态可以使用 `guest` 命名空间；登录后不要自动把 guest 缓存覆盖到账号缓存。
- 登出时保留该用户的非敏感搜索偏好，下一次登录可以恢复。
- 不在该缓存中保存护照号码、签证号码、生日或乘机人证件信息。

建议 key 前缀：

```text
search_preferences_v1_{userId}
```

### 4.3 保存时机

- 用户完成城市或机场选择后立即保存。
- 用户修改日期、停留天数或价格上限后，使用 300 毫秒 debounce 保存。
- 用户点击“搜索方案”时强制保存一次完整快照。
- 不要等 Activity 或进程销毁时才保存。

## 5. 智能出发日期规则

### 5.1 目标

日期规则必须可解释、可测试、不会选择过去日期，也不要让 AI 决定基础默认日期。

### 5.2 优先级

以设备当前时区的 `LocalDate.now()` 作为 `today`：

1. 缓存日期在 `today + 1 天` 到 `today + 365 天`之间时，原样恢复。
2. 缓存日期已过期时，使用历史 `preferredLeadDays` 和 `preferredDepartureDayOfWeek` 推算新的未来日期。
3. 有缓存但没有合法历史提前天数时，选择至少 21 天后的同一星期。
4. 第一次打开 App 或没有任何日期历史时，选择“至少 21 天后的第一个周五”。

### 5.3 推算算法

```text
MIN_LEAD_DAYS = 7
DEFAULT_LEAD_DAYS = 21
MAX_LEAD_DAYS = 180
MAX_SELECTABLE_DAYS = 365

if cachedDate is between today + 1 and today + 365:
    selectedDate = cachedDate
else if preferredLeadDays exists:
    leadDays = clamp(preferredLeadDays, 7, 180)
    candidate = today + leadDays
    selectedDate = candidate 向后移动到 preferredDepartureDayOfWeek
else:
    candidate = today + 21 days
    selectedDate = candidate 当天或之后的第一个 Friday
```

### 5.4 交互规则

- 日期区域展示“建议”标签时，只在系统自动推算日期后显示一次。
- 文案示例：`根据你上次的出行习惯，已更新为 9 月 25 日`。
- 用户手动修改后立即移除“建议”标签。
- 不重复显示同一个体验时间或日期说明。
- 日期选择器禁止选择今天以前的日期。
- 如果设备日期异常或解析失败，回退到 `today + 21 天后的第一个周五`。
- 服务端仍应校验日期，不能仅依赖 Android 客户端。

## 6. “使用当前城市”产品流程

### 6.1 入口设计

在“选择出发城市或机场”页面顶部搜索框下增加：

```text
[定位图标] 使用当前城市
           自动推荐附近机场
```

入口只用于出发地，不在目的地页面展示。

### 6.2 首次点击

1. 用户点击“使用当前城市”。
2. 页面解释用途：`仅用于推荐附近出发机场，不会持续追踪或上传你的位置。`
3. 请求 `ACCESS_COARSE_LOCATION`。
4. 授权后显示短暂加载状态：`正在查找附近机场...`。
5. 取得位置后在本地匹配城市和机场。
6. 匹配成功后进入该城市的二级机场选择页，不直接替用户提交。

### 6.3 匹配成功示例

```text
已定位到新加坡

推荐出发机场
● 新加坡樟宜机场 SIN · 约 18 km
○ 实里达机场 XSP · 约 14 km

[使用推荐机场]  [选择全部机场]
```

距离只能作为辅助信息，不应成为签证或航班资格判断依据。

### 6.4 权限和异常状态

| 状态 | 产品行为 |
| --- | --- |
| 首次未授权 | 请求大概位置权限 |
| 用户拒绝 | 提示“无法获取当前位置，你仍可手动选择城市” |
| 永久拒绝 | 提供“前往系统设置”和“继续手动选择” |
| 定位关闭 | 提供“开启定位服务”和“继续手动选择” |
| 获取超时 | 8 秒后停止加载并恢复手动选择 |
| Google Play services 不可用 | 不崩溃，隐藏重试或提示手动选择 |
| 找不到附近城市 | 展示最近三个支持的城市/机场，让用户确认 |
| 模拟器 | 支持使用 Emulator Extended Controls 注入经纬度测试 |

不要在 App 启动时主动弹定位权限。必须由用户点击“使用当前城市”触发。

## 7. 本地城市与机场匹配

### 7.1 数据要求

复用项目已有中英文城市与机场 JSON，为每个城市和机场补齐：

```json
{
  "cityCode": "SIN",
  "countryCode": "SG",
  "continentCode": "AS",
  "nameZh": "新加坡",
  "nameEn": "Singapore",
  "latitude": 1.3521,
  "longitude": 103.8198,
  "timezone": "Asia/Singapore",
  "popular": true,
  "airports": [
    {
      "iataCode": "SIN",
      "nameZh": "新加坡樟宜机场",
      "nameEn": "Singapore Changi Airport",
      "latitude": 1.3644,
      "longitude": 103.9915,
      "international": true,
      "atlasSearchEnabled": true
    }
  ]
}
```

### 7.2 匹配算法

- 使用 Haversine 公式在本地计算当前位置到城市中心和机场的距离。
- 优先筛选 `atlasSearchEnabled=true` 的机场。
- 先查找 120 公里内最近城市。
- 如果没有城市命中，返回 250 公里内最近三个支持机场供用户确认。
- 同一城市存在多个机场时进入二级机场列表，不强制只选最近机场。
- 城市级搜索默认选择该城市全部 `atlasSearchEnabled=true` 机场。
- 排序优先级：距离、国际机场、Atlas 可搜索、热门机场。

### 7.3 隐私边界

- 经纬度只在 Android 内存中参与匹配。
- 不写入 DataStore。
- 不上传后端。
- 缓存仅保存最终确认的城市代码、机场代码和选择来源。

## 10. 验收标准

### 10.1 缓存

- 用户设置 SIN、PVG、未来日期、1 至 3 天后关闭并重启 App，设置可以恢复。
- 用户 A 与用户 B 的缓存互不影响。
- 过去日期不会恢复到页面。
- 手动修改后的字段能够立即覆盖旧缓存。
- 缓存损坏时页面使用默认值，不崩溃。

### 10.2 日期

- 有效未来日期原样恢复。
- 昨天、今天和超过一年后的缓存日期会被修正。
- 第一次打开默认日期至少在 21 天以后且为周五。
- 用户历史提前天数可以滚动生成合理的未来日期。
- 自动建议文案只出现一次。

### 10.3 定位

- 模拟器定位到新加坡时推荐 SIN/XSP，并进入机场确认页。
- 仅授权大概位置也能完成城市匹配。
- 拒绝权限后仍能手动搜索城市。
- 关闭定位服务时不崩溃、不无限加载。
- 8 秒超时后恢复可操作状态。
- 不需要 Google Maps API Key 即可构建和运行。
- Android 不上传或持久化原始经纬度。

### 13.2 与本文档的三处有意偏离

1. **§5.2 第 3 条 vs §5.3 伪代码冲突**：优先级 3 按 §5.2 用「过期日期自身的星期」，`Friday` 只用于优先级 4（首次打开）。
2. **§7.2 排序含「国际机场」但未定义数据源**：改为 距离 → `atlasSearchEnabled` → 主门户(`defaultAirportIata`) → 热门榜 → IATA 字典序。
3. **定位优先级**：文档未指定，实现最初用 `PRIORITY_BALANCED_POWER_ACCURACY`，但它不唤起 GPS，在无网络定位的设备/模拟器上必然超时（实测 `ProviderRequest[OFF]`、`last location=null`）→ 改为 `PRIORITY_HIGH_ACCURACY`。**仅持有 `ACCESS_COARSE_LOCATION` 时系统只会回粗粒度位置**，因此隐私口径不变，只是允许使用 GPS provider。

另有两点实现口径需知：目录内 `XSP`（实里达）不在可搜机场目录中，因此新加坡只推荐 `SIN`；自动推算出的日期**不触发写盘**，避免污染 `preferredLeadDays` 习惯信号。

- **构建**：`./gradlew assembleDebug` → BUILD SUCCESSFUL，`app-debug.apk` 21.6 MB。
- **i18n 门禁**：`scripts/check-i18n.sh` → 332 个 key 中英齐全。
